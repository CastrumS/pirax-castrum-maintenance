# Plugin tests

These are Bun test suites for `plugin/pirax-form-test`. They run against a real, disposable WordPress with the licensed Gravity Forms plugin and Fluent Forms from wordpress.org:

- WordPress runs in WordPress Playground on `127.0.0.1`.
- A headless Chromium, driven through Playwright's library API, logs in, uploads the built ZIP and submits the rendered forms.

Nothing in authentication, form processing or validation is mocked. The only test doubles are:

- a `pre_wp_mail` observer that logs the final `wp_mail()` arguments and returns success instead of sending (`review-regressions.test.ts` removes it for its envelope checks and instead lets WordPress parse the headers into PHPMailer, where a `phpmailer_init` observer records the effective To/Cc/Bcc and throws before any transport; the plugin's own guard stays installed);
- a Google reCAPTCHA `siteverify` answer of `{"success":false}`, supplied via `pre_http_request`.

Because of the observer, these tests prove that recipients are transformed, **not** that mail is delivered.

## Prerequisites

- **Bun** runs the tests, the build and dependency installs.
- **Node:** Playground's native `fs-ext` addon cannot load under Bun, so `playground.ts` runs as a Node child process. The harness talks to it over a stdin/stdout PHP control protocol that uses Playground's own `run()` API. There is no HTTP backdoor.
- **Compiler toolchain** (`g++`, `make`, `python3`): `bun install` builds the addon with `node-gyp` when no prebuilt binary matches your Node version, which is the case for Node 26. After switching Node major versions, run `bun install` again.
- **`zip` and `unzip`** for the build, the version checks and trace scrubbing.
- **Chromium:** `bunx playwright install chromium`.
- **Network access** on the first run, to fetch WordPress 7.1.2 and Fluent Forms 6.2.14. The Fluent Forms ZIP is cached in `.cache/plugin-test/`.

The pinned versions are `@wp-playground/cli` 3.1.55, `playwright` 1.63.0, WordPress 7.1.2, PHP 8.3 and Fluent Forms 6.2.14. The Gravity Forms version is read from the licensed ZIP. The plugin accepts marked submissions only on GF 3.1.2.

## Credentials

The harness needs two environment variables. The tests check only whether they are present and fail with the variable's **name** when one is missing, never its value. They never skip silently.

| Name | What it is | How to get it |
|---|---|---|
| `GRAVITY_FORMS_ZIP` | Absolute path to the licensed Gravity Forms ZIP | gravityforms.com → account → Downloads |
| `FORM_TEST_TOKEN` | The operator's private, randomly generated shared marker token (16–255 characters of `[A-Za-z0-9._~+/=-]`) | Generated by the operator. The same value goes in the plugin settings and the form checker. |

These values live in the registered repository's `.env`. Do not copy, print, commit or edit environment files. The Node child receives `GRAVITY_FORMS_ZIP` but never the token.

From a git worktree, load the registered repository's file:

```sh
bun --env-file=<registered-repo>/.env test test/plugin/harness.test.ts
bun --env-file=<registered-repo>/.env run test:plugin
```

If both variables are already in the environment, plain `bun test` / `bun run test:plugin` works as well. No `--timeout` flag is needed: each suite calls `setDefaultTimeout(180_000)` (per file, because Bun 1.4 scopes it to the calling file and ignores a `bunfig.toml` timeout), since one Playground PHP round trip can exceed Bun's 5 s default. Site start-up hooks and long scenarios keep explicit, longer timeouts. A new suite must set it too.

## Commands

```sh
bun install
bunx playwright install chromium
bun run build:plugin        # the suites also rebuild before uploading
bun --env-file=<registered-repo>/.env test test/plugin/core.test.ts
```

| Suite | Covers |
|---|---|
| `harness.test.ts` | Preflight messages, the Playground site, wp-admin login and upload, unmarked submissions, the network ledger and manifest, token scrubbing |
| `core.test.ts` | ZIP contents, upload and activation without the form plugins, capability and nonce settings flow, marker parsing, mail transformation, uninstall |
| `adapters.test.ts` | GF/FF marked and unmarked submissions with controls, CAPTCHA, fail-closed integrations, FF queued, retried and legacy-batch jobs, token rotation, the hourly sweep |
| `safety.test.ts` | Late FF feed filter, a throwing queued notification, a marked entry deleted natively while its queued job runs, rejection before CAPTCHA, GF queue pruning in the sweep, the exact version gate |
| `review-regressions.test.ts` | Review round 1: the native PHPMailer envelope (stopped before transport) for control-padded Cc/Bcc header names, and the sweep after the marker's FF field is renamed or removed |

Each suite starts its own site, which takes about a minute. Budget roughly 10 minutes for the whole plugin suite.

## Harness

- **`harness.ts`** (`startHarness({ run })`): preflight, the Playground child, serialized `php()` execution, logs, and queue control. `drainQueues()` fires the native GF, Action Scheduler and FF runners through their own anonymous `admin-ajax.php` requests. `runCron(hooks)` makes the named events due and runs a real `wp-cron.php` request. Bounded waits fail with a redacted tail of `playground.log`.
- **`fixtures.php`:** users (editor, subscriber), the GF and FF forms, the reCAPTCHA forms, the unsupported (post-field and payment) forms, notifications with To/Cc/Bcc, and native feed records.
- **`mu-plugin.php`** (test-only, never packaged):
  - the mail and `siteverify` observers;
  - real GF feed add-on and FF integration ledger feeds;
  - option-driven fixtures, all off by default: FF native email queueing, GF background feeds, failing or throwing mail, direct-dispatch integrations, competing filters, a late FF feed-type filter, and a native FF entry deletion inside a runner's notification job;
  - Action Scheduler's loopback runner is disabled so the harness drives queues deterministically.

## Evidence and privacy

Each harness run writes `artifacts/plugin/<suite>-<timestamp>/`:

| File | Content |
|---|---|
| `manifest.json` | Suite and scenarios (browser contexts), WordPress/PHP/GF/FF versions, fixture ids, SHA-256 of both form-plugin ZIPs, the name and SHA-256 of every uploaded ZIP (the built `dist/pirax-form-test.zip` when under test), and the artifact paths below |
| `mail.jsonl`, `feeds.jsonl`, `entries.json` | Final `wp_mail()` arguments, native feed executions, remaining entries |
| `network.jsonl` | One line per browser response or failed request: context, method, URL, status, resource type. No headers, cookies or bodies. |
| `<scenario>.trace.zip` | Playwright action trace. Open it with `bunx playwright show-trace`. |
| `playground.log` | Redacted Playground output |
| `queue-states.jsonl` | Adapter and safety suites only: queue ids and statuses per step |

Network data is kept in a separate ledger because Playwright records network in a trace only together with DOM snapshots, and snapshots would retain typed secrets. Traces therefore have screenshots, snapshots, sources and video disabled.

Every retained file is redacted for the token and the GF ZIP path, in raw, URL-encoded and JSON-escaped forms. Traces are unpacked, scrubbed and repacked. The suites assert with `findSecret()` that no form remains, and `harness.test.ts` puts the token into a URL and a typed field to prove it. Neither the GF sources nor the ZIP are copied into artifacts.

`dist/`, `artifacts/` and `.cache/` are ignored by git.
