# Plugin tests

These are Bun test suites for `plugin/pirax-form-test`. They run against a real, disposable WordPress with the licensed Gravity Forms plugin and Fluent Forms from wordpress.org. Two suites add the [full compatibility stack](#full-compatibility-stack): licensed Fluent Forms Pro, CleanTalk and FluentSMTP.

- WordPress runs in WordPress Playground on `127.0.0.1`.
- A headless Chromium, driven through Playwright's library API, logs in, uploads the built ZIP and submits the rendered forms.

Nothing in authentication, form processing or validation is mocked. The only test doubles are:

- a `pre_wp_mail` observer that logs the final `wp_mail()` arguments and returns success instead of sending (`review-regressions.test.ts` removes it for its envelope checks and instead lets WordPress parse the headers into PHPMailer, where a `phpmailer_init` observer records the effective To/Cc/Bcc and throws before any transport; the plugin's own guard stays installed);
- a Google reCAPTCHA `siteverify` answer of `{"success":false}`, supplied via `pre_http_request`.

The updater suite needs no HTTP double: WordPress fetches a [loopback release fixture](#update-and-release-tests) over real HTTP.

On the full compatibility stack the mail observer passes mail on to FluentSMTP's Simulator, and a test-only HTTP transport answers or blocks third-party requests; see [below](#full-compatibility-stack).

Because of the observer, these tests prove that recipients are transformed, **not** that mail is delivered. The full stack's Simulator is not delivery either.

The [forms checker suites](../forms/README.md) reuse this native harness with real wp-admin settings, production browser/CLI dispatch and scoped R2 reports. Their Playground confirmations must truthfully time out over IMAP; the separate `mail:selftest` sends one real SMTP message and leaves it in the dedicated mailbox. The checker wrapper additionally sanitizes credential/address values with the production redactor before retaining evidence; do not assume this plugin harness's token/ZIP-only redaction covers other credentials.

## Prerequisites

- **Bun** runs the tests, the build and dependency installs.
- **Node:** Playground's native `fs-ext` addon cannot load under Bun, so `playground.ts` runs as a Node child process. The harness talks to it over a stdin/stdout PHP control protocol that uses Playground's own `run()` API. There is no HTTP backdoor.
- **Compiler toolchain** (`g++`, `make`, `python3`): `bun install` builds the addon with `node-gyp` when no prebuilt binary matches your Node version, which is the case for Node 26. After switching Node major versions, run `bun install` again.
- **`zip` and `unzip`** for the build, the version checks and trace scrubbing.
- **Chromium:** `bunx playwright install chromium`.
- **Network access** on the first run, to fetch WordPress 7.1.2, Fluent Forms 6.2.14, CleanTalk 6.88 (`cleantalk-spam-protect`) and FluentSMTP 2.4.1 from wordpress.org. The ZIPs are cached in `.cache/plugin-test/` and their `Version` headers are checked.

The pinned versions are `@wp-playground/cli` 3.1.55, `playwright` 1.63.0, WordPress 7.1.2, PHP 8.3, Fluent Forms 6.2.14, CleanTalk 6.88 and FluentSMTP 2.4.1. The Gravity Forms and Fluent Forms Pro versions are read from the licensed ZIPs; the harness requires Pro 6.2.15 exactly. The plugin accepts marked submissions only on GF 3.1.2 and the other exact versions in the [plugin guide](../../plugin/pirax-form-test/README.md#supported-versions-and-behaviour).

## Credentials

The harness needs these environment variables. The tests check only whether they are present and fail with the variable's **name** when one is missing or invalid, never its value. They never skip silently.

| Name | What it is | How to get it |
|---|---|---|
| `GRAVITY_FORMS_ZIP` | Absolute path to the licensed Gravity Forms ZIP | gravityforms.com → account → Downloads |
| `FORM_TEST_TOKEN` | The operator's private, randomly generated shared marker token (16–255 characters of `[A-Za-z0-9._~+/=-]`) | Generated by the operator. The same value goes in the plugin settings and the form checker. |
| `FLUENT_FORMS_PRO_ZIP` | Absolute path to the licensed Fluent Forms Pro **6.2.15** ZIP. Needed only by the full-stack suites (`stack-harness.test.ts`, `compatibility.test.ts`), which `test:plugin` and `bun test` include. | fluentforms.com → account → Downloads |

`PIRAX_HELPER_SIGNING_KEY`, the real release signing seed, is never needed by the tests. If it is in the environment anyway, the build checks that no packaged file contains it and withholds it from `zip`/`unzip`, the Playground child and Chromium; the core suite also scans `dist/` for it.

These values live in the registered repository's `.env`. Do not copy, print, commit or edit environment files. The Node child receives `GRAVITY_FORMS_ZIP`, and `FLUENT_FORMS_PRO_ZIP` only for the full stack, through its environment only, never its command line. It never receives the token. ZIP versions are read with the ZIP on `unzip`'s stdin, so no licensed path appears on a command line.

From a git worktree, load the registered repository's file:

```sh
bun --env-file=<registered-repo>/.env test test/plugin/harness.test.ts
bun --env-file=<registered-repo>/.env run test:plugin
```

If both variables are already in the environment, plain `bun test` / `bun run test:plugin` works as well. No `--timeout` flag is needed: each suite calls `setDefaultTimeout(180_000)` (per file, because Bun 1.4 scopes it to the calling file and ignores a `bunfig.toml` timeout), since one Playground PHP round trip can exceed Bun's 5 s default. Site start-up hooks and long scenarios keep explicit, longer timeouts. A new suite must set it too.

## Harness

- **`harness.ts`** (`startHarness({ run })`): preflight, the Playground child, serialized `php()` execution, logs, and queue control. `drainQueues()` fires the native GF, Action Scheduler and FF runners through their own anonymous `admin-ajax.php` requests. `runCron(hooks)` makes the named events due and runs a real `wp-cron.php` request. Bounded waits fail with a redacted tail of `playground.log`. `startHarness({ run, compatibility: true })` starts the full stack; see below for its additions.
- **`fixtures.php`:** users (editor, subscriber), the GF and FF forms, the reCAPTCHA forms, the unsupported (post-field and payment) forms, notifications with To/Cc/Bcc, and native feed records.
- **`mu-plugin.php`** (test-only, never packaged):
  - the mail and `siteverify` observers;
  - real GF feed add-on and FF integration ledger feeds;
  - option-driven fixtures, all off by default: FF native email queueing, GF background feeds, failing or throwing mail, direct-dispatch integrations, competing filters, a late FF feed-type filter, and a native FF entry deletion inside a runner's notification job;
  - full-stack fixtures, also off by default: `pirax_harness_gf_ajax` renders GF forms with the modern AJAX submission method; `pirax_harness_ct_rebind` wraps CleanTalk's FF closure so it still runs but cannot be recognized; `pirax_harness_ct_ajax_rebind` rebinds CleanTalk's generic AJAX check (`ct_ajax_hook`) on `plugin_loaded`, before any `plugins_loaded` callback: `'wrap'` wraps it (unrecognizable), `'early'` moves it to priority 1; `pirax_harness_gf_dynamic_field` (a GF form id) adds a field `input_50` to that form through GF's `gform_form_post_get_meta` filter; `pirax_harness_gf_ajax_version` sets GF's runtime `GFForms::$version` on admin-ajax requests only (elsewhere GF would run its upgrade routine); `pirax_harness_gf_meta_probe` logs each read of GF's form meta table during `plugins_loaded` to `gf-meta.jsonl` (admin-ajax action and request path only), leaving the query unchanged; `pirax_harness_ct_skip_probe` logs where CleanTalk reports skipping a check it ran (its `apbct_skipped_request` action) to `ct-skips.jsonl` (file basename, function, line and reason only); `pirax_harness_ct_late` re-registers CleanTalk's real checks between classification and dispatch; `pirax_harness_render_probe` snapshots every GF/FF hook binding and counts option writes around the settings page; `pirax_harness_ff_pro_feature($form_id, 'double_optin'|'admin_approval'|'auto_delete', bool)` writes Pro's native settings;
  - an `activations.jsonl` ledger of every activated plugin, which shows the mu-plugin was loaded during activation;
  - Action Scheduler's loopback runner is disabled so the harness drives queues deterministically.

The mu-plugin is written before any plugin is installed, so its safeguards are active during every activation request.

## Full compatibility stack

`startHarness({ run, compatibility: true })` also installs and activates Fluent Forms Pro (from `FLUENT_FORMS_PRO_ZIP`), CleanTalk 6.88 and FluentSMTP 2.4.1 after GF and FF. The default stack is unchanged: only GF and FF, no Pro prerequisite, and `h.compatibility` is `false`.

**Setup.** The blueprint defines `FLUENTMAIL_SIMULATE_EMAILS` before any request, so FluentSMTP hands mail to its Simulator provider. `fixtures.php` keeps CleanTalk's WordPress HTTP API mode and contact-form check on, seeds its moderation server as `https://moderate.cleantalk.org`, consumes its one-shot activation redirect, enables Pro's `webhook` module and adds one enabled Pro WebHook feed on the FF form, pointing at a loopback capture URL (`h.fixtures.stack`). GF has no Pro feed.

**Transport containment.** CleanTalk 6.88 calls `WpOrg\Requests\Requests::request()` directly, even in its "WordPress HTTP API" mode, so it bypasses `pre_http_request`; a filter there would record a false zero. The mu-plugin therefore installs a test-only `Pirax_Harness_Transport` as the only Requests transport. Loopback requests go to the real transport. CleanTalk `check_message`/`check_newuser` requests get a successful moderation answer and the capture URL gets a success response. Every other third-party request is blocked with a `WP_Error`. Answered and blocked requests are logged in `http.jsonl`. The reCAPTCHA double at `pre_http_request` still answers first. Browser contexts abort every http(s) request to a host other than the site's own, including CleanTalk's bot detector and telemetry scripts.

This covers PHP HTTP through Requests (`wp_remote_*` and direct Requests calls) and the browser only. It is **not** a general network sandbox: raw PHP cURL or sockets bypass it, and Playground 3.1.55 always enables PHP networking. CleanTalk's direct transport is used only after it switches off its WordPress HTTP API mode on a network failure; the successful moderation answer avoids that, and the suites assert the mode is still on after their controls. Exploratory runs made before browser containment existed did reach CleanTalk's external assets and telemetry.

**Mail.** On the full stack the `pre_wp_mail` observer records the `wp_mail()` arguments and lets the call continue (option `pirax_harness_mail_passthrough`, on by default here; set it `false` to restore the short-circuit). Passthrough also requires the Simulator constant and FluentSMTP's `wp_mail`, so mail never reaches PHP mail or SMTP. There are three separate views:

- `h.mail()`: the `wp_mail()` arguments, as on the default stack;
- `h.envelopes()`: the effective PHPMailer envelope at `phpmailer_init` (To, Cc, Bcc, Reply-To, From, subject, headers, `mailer`, `transport`), which is what FluentSMTP hands to its provider;
- `h.simulator()`: FluentSMTP's own `fsmpt_email_logs` rows for the Simulator provider. They have no Cc/Bcc, so use `envelopes()` for those.

This proves what FluentSMTP 2.4.1 hands to its provider in simulation. It does not prove real SMTP/IMAP delivery, other providers or other 2.4.x releases.

**Readers.** All additive; existing harness contracts are unchanged.

- `h.compatibility`, and `h.versions` with `ffPro`, `cleantalk` and `fluentSmtp` set on the full stack only. The pins are exported as `FF_PRO_VERSION`, `CLEANTALK_VERSION` and `FLUENT_SMTP_VERSION`.
- `h.http()`: `{ purpose: "cleantalk-moderation"|"webhook-capture"|"blocked", method, host, path, hooks, action, api?, entry?, carriesToken, request, time }`, with no query, header or body value. `request` is the path of the incoming WordPress request that made the call, without its query (which can hold nonces); the shared logger's raw `REQUEST_URI` is not used for this ledger. `carriesToken` says whether the outgoing URL or body held the configured marker token, raw, URL-encoded or JSON-escaped; only the boolean is kept. The file is append-only, so slice by its length before a step. Use `hooks` to separate submission traffic from activation and background traffic: FF moderation runs under `wp_ajax_nopriv_fluentform_submit` and `fluentform/before_insert_submission`, GF postback moderation under `gform_entry_is_spam`, GF modern AJAX moderation (CleanTalk's generic check) under `plugins_loaded` with `action` `gform_submit_form`, and the webhook under `fluentform/integration_notify_fluentform_webhook_feed` with `entry` set. CleanTalk's browser pre-submit email check (`/wp-json/cleantalk-antispam/v1/check_email_before_post`, to `api.cleantalk.org`) is logged as `blocked`; marked-submission assertions exclude only that exact REST path, because it happens before the marked POST.
- `h.envelopes()`, `h.simulator()`: as above.

Pro webhook jobs run from Action Scheduler: nothing reaches the capture URL before `drainQueues()`.

**Wrong-version fixtures.** `compatibility.test.ts` edits the version declaration of the installed plugin inside the disposable site (CleanTalk to 6.88.1, Pro to 6.2.16, FluentSMTP to 2.4.2), makes fresh requests and restores the file. It asserts the restored file's SHA-256 equals the original, and keeps the original and altered hashes in `compatibility-notes.jsonl`. No production override exists for this.

## Update and release tests

**Updater (`updates.test.ts`, credentials as above).** `update-fixture.ts` serves a loopback HTTP release channel on `127.0.0.1` laid out like the repository's GitHub releases, signs manifests with a fresh in-memory Ed25519 test key, and builds staged helper ZIPs with the shipping build's allowlist. Only those disposable copies get the fixture's release root and test public key; the first test asserts the shipping source still holds the production root and key. There is no runtime setting or filter that changes the channel or key. This proves that an updater-equipped helper updates itself, not that a 0.2.4 site can (it needs one manual upload).

**Release CLI (`release.test.ts`).** Needs no `.env`. The whole suite needs network and an authenticated `gh`, because its GitHub lookups are real; the cases named `offline:` (dry run, import, seeds, key mismatch, local tag, source facts and privacy, seed scan) need neither and can be run alone:

```sh
bun --no-env-file test test/plugin/release.test.ts                 # everything, real read-only GitHub lookups
bun --no-env-file test test/plugin/release.test.ts -t '^offline:'  # only the cases that never reach GitHub
```

Each case copies the scripts and helper source into a disposable git checkout and runs the real `bun scripts/release-plugin.ts` there, so this repository's `dist/` and tags are never touched. Seeds are generated per test and given only to that child's environment. A `gh` wrapper on the checkout's `PATH` records every call and passes only two exact read-only shapes to the real `gh`: `gh api --include repos/…/git/ref/tags/<tag>` and the paginated release listing. Every other call, including the tag-ref `POST` and `gh release create`, is answered by the wrapper (success, or a failure the test selects), so no tag, ref, release or secret is ever created; authentication is never faked, and the publish cases prove the calls the CLI makes, not a real publication. Cases:

- dry run: three assets; the signature verifies with the test public key in raw 32-byte base64 form (as in the plugin) and not with the production key; ZIP SHA-256, package URL and version match; an `AUDITED_VERSIONS` edit in the copy reaches the manifest; every ZIP entry equals its source file; no `gh` call;
- importing the script prints, writes and calls nothing;
- unset, empty, non-base64, 31- and 64-byte, unpadded, newline-padded and base64url seeds fail in both modes with the variable's name only, before anything is built;
- publishing with a key that does not match the production key, or with an existing local `v<version>` tag, fails before any `gh` call;
- a real GitHub lookup with an invalid token (HTTP 401) stops publishing; `remoteTag()` answers `absent` for a missing tag and `present` for an existing one (`cli/cli` `v2.0.0`);
- the wrapper itself, with an invalid token, forwards the two lookups (GitHub answers 401) and answers a ref `POST`, a `DELETE`, a field-implied `POST`, any other `GET` and `gh release create` without forwarding them;
- a full publish of an unreleased version `0.0.1` makes the read-only lookups, then exactly the claim `gh api --method POST repos/CastrumS/pirax-castrum-maintenance/git/refs -f ref=refs/tags/v0.0.1 -f sha=<commit>` and one `gh release create v0.0.1 --repo CastrumS/pirax-castrum-maintenance --verify-tag --latest --target <commit>` with the three assets;
- a claim refused as already existing (HTTP 422) or failing without an answer stops before `gh release create`; a release failure after the claim exits 1, names the claimed tag and requires inspecting remote tag/release state before recovery, and makes no further call (no retry, overwrite or delete);
- a header that differs from `VERSION`, a prerelease version, and duplicated or non-literal `AUDITED_VERSIONS` lines are refused; a generated seed used as the version is refused by field name in both modes, and the test keeps only whether the output contained it (a run whose output does is logged as withheld);
- a seed placed in a source file is refused by the parent's scan, and `findSecret()` finds no private key form in the retained logs, manifests and every checkout's `dist/`.

## Evidence and privacy

Each harness run writes `artifacts/plugin/<suite>-<timestamp>/`:

| File | Content |
|---|---|
| `manifest.json` | Suite and scenarios (browser contexts), WordPress/PHP/GF/FF versions (plus Pro, CleanTalk and FluentSMTP on the full stack), fixture ids, SHA-256 of both form-plugin ZIPs (all five plugin ZIPs on the full stack), the name and SHA-256 of every uploaded ZIP (the built `dist/pirax-form-test.zip` when under test), and the artifact paths below |
| `mail.jsonl`, `feeds.jsonl`, `entries.json` | Final `wp_mail()` arguments, native feed executions, remaining entries |
| `network.jsonl` | One line per browser response or failed request: context, method, URL, status, resource type. No headers, cookies or bodies. |
| `<scenario>.trace.zip` | Playwright action trace. Open it with `bunx playwright show-trace`. |
| `playground.log` | Redacted Playground output |
| `queue-states.jsonl` | Adapter and safety suites only: queue ids and statuses per step |
| `http.jsonl`, `envelopes.jsonl`, `simulator.jsonl` | Full stack: contained HTTP ledger, effective envelopes and FluentSMTP Simulator rows (see above). Not written on the default stack. |
| `compatibility-notes.jsonl` | `compatibility.test.ts` only: control ids, HTTP and job counts per window, Pro feature states, the auto-delete runner state, version-gate outcomes and the original/altered vendor-file hashes |
| `update-summary.json`, `update-requests.jsonl` | `updates.test.ts` only: versions, manifest and ZIP digests, the test keys' public fingerprints and each case's result; the fixture's request ledger (method, path, status, WordPress user agent) |

`release.test.ts` writes `artifacts/plugin/release-<timestamp>/` instead, without a harness: one `<case>.log` per CLI run (exit code, output, recorded `gh` calls and `dist/` listing), the dry run's manifest and `.sig`, and `release-summary.json`. Generated private test keys are never retained. Most stay in memory, but two privacy regressions write one on purpose: the source-privacy case uses a generated seed as the helper version, and the seed-in-source case appends one to the helper README. Each is committed only to its disposable checkout, which `afterAll` deletes, and the CLI must refuse it. No production seed is ever written. Only public fingerprints are retained, and the suites assert with `findSecret()` that no private key form appears in their evidence.

Network data is kept in a separate ledger because Playwright records network in a trace only together with DOM snapshots, and snapshots would retain typed secrets. Traces therefore have screenshots, snapshots, sources and video disabled.

Every retained file is redacted for the token and both licensed ZIP paths (GF and, on the full stack, Pro), in raw, URL-encoded and JSON-escaped forms. Traces are unpacked, scrubbed and repacked. The suites assert with `findSecret()` that no form remains, and `harness.test.ts` puts the token into a URL and a typed field to prove it. No licensed or vendor sources or ZIPs are copied into artifacts.

Redaction covers retained artifacts, not the test runner's own output. A failing matcher can print the value it received. Tests whose subject could hold a credential (such as a preflight result) use synthetic stand-in inputs, never the real variables.

`dist/`, `artifacts/` and `.cache/` are ignored by git.
