## Acceptance criteria (before test implementation)

**AC1 — One pin authority.** PHP `AUDITED_VERSIONS` is the sole executable source for all five vendor pins. Harness downloads/version checks, native expected values, wrong-version fixtures and release manifests consume it. Missing/duplicate/unknown keys, nonliteral values or malformed source are errors. No fixed audited-vendor version remains in `test/plugin/*.test.ts`. Deliberate mismatches are derived and guaranteed different. A shipping helper patch bump does not break its own native/release tests. `test/forms/harness.ts` follows the same pins.

**AC2 — Discovery and package identity.** Daily and manual runs resolve all five current upstream versions, downloading through wordpress.org or the official GPL Vault updater only. A complete unchanged matrix does not audit, change pins or publish. Any unresolved plugin, malformed response, unsupported version, regression, failed download, invalid ZIP or mismatched main-file Version header fails closed. A changed matrix downloads all five packages; native manifests prove the tested packages have the selected versions and digests.

**AC3 — Paid lifecycle.** Decrypt the committed encrypted official updater, install it in an isolated WordPress 7.1.2/PHP 8.3 Playground, activate its license, save enabled API settings, update the updater itself before querying products, fetch the two paid packages, and deactivate before the test/publication gate. Success, no-change and catchable failure paths confirm deactivation. Retain only safe lifecycle facts and, where exposed by the official client, before/after activation counts. A cleanup refusal/unknown outcome is a failure, not a successful download. First live proof must establish unchanged activations, not merely that a finally block was entered.

**AC4 — Audit gate.** Candidate pins in an isolated checkout plus the exact selected packages pass `bun test test/plugin` with Node 24, Bun 1.4.2 and Chromium. The full-stack panel and native unaudited-callback/suppression assertions remain the hook-inventory comparison. Do not weaken callbacks, expected mail/HTTP isolation, fixture version mismatch checks or skip a suite to accept a candidate. Only then prepare a helper patch bump and publish. No LLM/code-diff audit is introduced.

**AC5 — Publication.** On a passing changed candidate, main receives a fast-forward pin/helper-version/documentation commit and the existing release script publishes the matching v0.3.x ZIP, manifest and signature. Independent verification confirms the shipping public key, exact manifest bytes, ZIP hash, manifest pins and remote tag commit. Wrong branch, changed main since audit, existing tag/release, failed audit, failed cleanup, invalid candidate or failed pre-publication privacy check publishes nothing. A publish error after a remote mutation is reported as potentially partial, never as guaranteed rollback.

**AC6 — Negative/no-change decisions.** Fixture tests cover no change, numeric ordering (including multi-digit components), download failure, GPL Vault refusal, suite failure, cleanup failure, tag exists, main advancing, corrupt/missing candidate, and publication uncertainty. No-change makes no pin commit/release; only the independently due heartbeat below is allowed. Failed candidates cannot become publishable through a default/missing result or an `always()` path.

**AC7 — Notice.** Catchable discovery, setup, download, audit, cleanup, push and publication failures attempt one bounded real SMTP email per audit run to piraxcastrum@gmail.com, subject beginning `[pirax-audit]`, naming safe old/candidate versions, failing stage and run URL. It contains no credential, paid URL, raw vendor response or uncontrolled exception. SMTP failure leaves the job failed and a safe explicit secondary error. A controlled failure invocation proves real SMTP authentication/acceptance and mailbox arrival without changing pins or publishing.

**AC8 — Scheduling and heartbeat.** Daily schedule plus `workflow_dispatch` on main, a repository-wide re-audit concurrency group with `cancel-in-progress: false`, and a heartbeat commit when main's last commit is at least 30 days old. A separate lightweight same-host watchdog checks missed/disabled audit runs and attempts email when the last started audit is over 48 hours old. Test timing boundaries and watchdog failure handling. Document that neither same-host schedules nor email can guarantee notification during a total Actions/SMTP outage.

**AC9 — Privacy and provisioning.** All six repository secrets (the five brief names plus PIRAX_HELPER_SIGNING_KEY) exist by name before live workflow verification; only the encrypted updater is committed. Signing credentials are not delivered to vendor acquisition or tests. GPL Vault/Gmail credentials are not passed to test/browser children. All retained logs, summaries, trace ZIP contents and final release assets pass `findSecret`; tests of leaking inputs use synthetic credentials. No plaintext updater, paid package, private URL, private seed or environment file is committed or uploaded as an artifact.

**AC10 — Regression checks and documentation.** `bun run typecheck`, `bun --env-file=.env test test/plugin` and `bun --env-file=.env test` pass for the checked-in baseline refactor. Build the plugin before the full suite. Updated guides explain scheduling, secrets, encrypted client setup, exact audit gate, failure email, heartbeat/watchdog, manual run and partial-release recovery. Candidate/published pins do not leave executable old-version assumptions behind.

**AC11 — Real end-to-end evidence.** After the reviewed workflow exists on main, run `gh workflow run reaudit.yml --ref main --repo CastrumS/pirax-castrum-maintenance`; retain the real run ID/URL, sanitized log/summary, activation cleanup evidence, and verified release or received failure email. The planned initial FF transition is 6.2.14 → 6.2.15. Keep a 6.2.15 discovery regression fixture. A failure email satisfies the brief's alternative operational proof but is not evidence that 6.2.15 was audited or that spok-ing can unblock.

## Stable decisions

### D1 — Keep the PHP literal table, share a narrow reader

Do not add a second JSON table, generated PHP copy or runtime setting. Add import-safe `scripts/plugin-source.ts` with a typed five-key `AuditedVersions`, strict literal parsing/reading, and shipping-helper header/constant version reading. Use the same pin reader from the release script, harness and re-audit scripts. Preserve release refusal of duplicate/nonliteral declarations and add validation of the complete known key set and stable numeric values.

`plugin/pirax-form-test/includes/compatibility.php` remains the pin source and runtime PHP behavior is unchanged. `test/plugin/harness.ts` exports existing FF/Pro/CleanTalk/SMTP constants as derived values and adds GF_VERSION. Validate both licensed ZIPs against their pins. Preserve WordPress/PHP pins as separate platform constants; they are not re-audited vendor packages.

### D2 — Make native tests resilient without weakening their oracles

Refactor core/harness/stack/safety/compatibility/release expectations and version-in-source mutation fixtures to use pins. A small `test/plugin/version-fixtures.ts` derives next numeric version, shorter/longer forms, prerelease and unreadable cases; ensure each intended mismatch is different even after multiple future bumps. Retain exact mismatch messages, restored-file hashes and unsupported-module assertions.

Release/core tests must read shipping helper metadata or normalize disposable fixtures to a declared test version instead of searching for shipping 0.3.0. Keep explicit synthetic helper-update versions in `updates.test.ts`: they test protocol ordering, not production pin configuration. Similarly, WP/PHP versions and loopback IPs are not forbidden audited-plugin literals. Replace the unrelated real FF download URL in update tests with one derived from its pin. Include the new shared source helper in release-test disposable checkouts.

Remove the independent GF/FF requirement from `test/forms/harness.ts` in favor of the shared pins. Do not rewrite checker parser fixtures that deliberately contain arbitrary reported versions: the checker does not maintain an audit table.

### D4 — Official updater only, with a short license lifetime

Implement `scripts/reaudit/gplvault-playground.ts` as a Node 24 child using `runCLI`, real networking and only the decrypted official updater. Reuse the Playground mechanism, not the normal harness (its test HTTP containment and required form plugins are inappropriate for real acquisition). Feed configuration through private stdin/environment, never argv. WP/PHP versions use shared platform facts.

Follow the design-proven sequence: `gv_api_manager()->set_api_key()->set_product_id()->activate()`, save API settings and enable activation status, run native plugin self-update for gplvault-updater, then use a fresh PHP request so the new client code is loaded. Add `gplvault_schema_payload` for the two main files at their pins; interpret official responses, resolve item IDs, call `download(['product_id' => item])`, and download while the activation is valid. Do not reimplement the REST protocol or mock live auth.

The parent owns cleanup. Mark activation as attempted before calling it (a lost response can still consume a seat); perform bounded deactivation in `finally`, including no-change and caught failures, and handle SIGTERM/SIGINT while the child is alive. Do not kill the Playground before cleanup finishes. Destroy decrypted ZIP, WordPress state and paid temporary files after their use. Fail before any publishable output if deactivation is refused or unconfirmed. SIGKILL/runner loss cannot execute finally; preserve that limitation and include the throwaway site's safe identifier/recovery guidance, not license data.

### D5 — Provision narrowly, then leave credentials out of the audit

Add `scripts/reaudit/setup.ts`, explicitly invoked only for one-time setup, not on import or every audit. Through `bun --env-file=.env`, stream existing GPL Vault/Gmail values to `gh secret set <NAME> --repo CastrumS/pirax-castrum-maintenance` on stdin; report names/results only. Preserve the existing signing key and verify its repository-secret name, not its value.

Generate a strong random GPLVAULT_UPDATER_PASSPHRASE in memory; GPG-encrypt the operator's official ZIP to `.github/audit/gplvault-updater.zip.gpg`, with passphrase on a private descriptor (`--passphrase-fd 3`, batch/loopback). Stream that same passphrase to the repository secret. Verify round-trip ZIP digest/version without printing plaintext or passphrase. Set the secret and commit the matching ciphertext as a coordinated setup operation; never rotate one alone during retries. Do not overwrite an existing ciphertext/secret automatically. Source ZIP presence has been checked; no operator download is presently required. No script reads or rewrites an environment file itself.

At runtime decrypt only in private runner scratch. Scope environment per operation: GPL Vault inputs to acquisition only, random per-run FORM_TEST_TOKEN and ZIP paths to suites, IMAP credentials to notification only, signing key to publication only. Disable persisted checkout credentials. Captured child output must be sanitized before it reaches stdout, summaries or uploaded logs; Actions masking alone is insufficient for encoded values or paid URLs.

### D6 — A closed decision state machine and safe candidate handoff

`scripts/reaudit/decide.ts` is pure and accepts explicit facts; `run.ts` executes operations and records a bounded safe summary. Model outcomes as `unchanged`, `failed` or `audited-candidate`, never a loose boolean default. `audited-candidate` requires complete versions/digests, all native suites passed, cleanup confirmed and evidence privacy passed.

Candidate metadata includes schema version, run ID, exact audited base commit, old and proposed complete pins, package SHA-256 values, gate outcomes, expected next helper patch and a digest of deterministic intended source changes. It includes no local ZIP paths, URLs, source ZIPs or executable patch supplied by a vendor. The publishing job reconstructs changes with checked-in code and rejects extra keys/invalid data or artifacts from any other run. Do not consume fork/PR artifacts or use `pull_request_target`.

### D7 — Reconstruct and publish the audited change, with no force push

`scripts/reaudit/bump.ts` narrowly rewrites the unique PHP table and matching helper Version header/VERSION constant and updates only generated current-version doc sections. It fails on malformed/ambiguous source. Baseline checkout pins remain unchanged in this leaf's implementation; the first real workflow performs the first live pin bump.

In the audit checkout, modify candidate pins and run the full plugin gate. After it passes, increment the helper patch, regenerate the current-version documentation, and run typecheck plus core/release regression checks against the final candidate. Record deterministic changes for the publisher. Do not widen callback inventories automatically if a new vendor version fails.

The publication job checks out the recorded base from main, validates the candidate, reconstructs exactly those changes, and checks remote main still equals the audited base. If main advanced, fail/email and require a new audit on the new base; do not rebase an already-tested candidate or force push. Check target tag/release absence before committing, then make an allowlisted commit and push HEAD to main normally. Run the existing `scripts/release-plugin.ts` with the matching signing key and GH_TOKEN from the Actions token. Its atomic tag claim remains authoritative even after a preflight. Verify the three remote assets independently after publish.

A main commit followed by failed publication is possible. Do not auto-revert, delete remote tags, overwrite releases, skip to a new patch version or falsely report no remote effect. Include stage, intended commit/tag and inspection instructions in the failure email. A subsequent unchanged run must surface an incomplete release for the current helper version rather than silently declaring the release healthy; inspection/recovery follows the existing release guide.

### D8 — Workflow permissions, concurrency and heartbeat

`.github/workflows/reaudit.yml`: daily off-the-hour UTC cron (e.g. `17 3 * * *`) plus manual dispatch, main-only publishing, fixed repository-wide concurrency group and no cancel-in-progress. Use explicit Node 24/Bun 1.4.2, frozen dependency install, native toolchain, GPG/zip/unzip/gh and Playwright Chromium with OS dependencies. Give audit ample timeout (at least 90 minutes), reserving cleanup time.

Separate jobs so the job that installs/runs vendor code has read-only repository access and no signing key. A write-capable publisher runs only on this run's explicit successful changed candidate; it does not run vendor PHP. A notification job with `if: always()` observes failed/cancelled required jobs, including setup failures, and sends one summary. Signing never depends on an `always()` success assumption. Broad checker/R2 tests remain local leaf regression checks, not new cloud secrets or a different audit-depth gate.

Heartbeat is an independent final maintenance path, not part of candidate pin changes. Under the same concurrency lock, fetch fresh main, calculate last-commit age in UTC, and update only `.github/audit/heartbeat.txt` when age is >=30 days. Recheck main and push fast-forward only. Run this also after a failed audit so weeks of gate failures do not disable the schedule. A successful audit/main commit suppresses an unnecessary heartbeat. No tag or helper release accompanies a heartbeat. Design note: the brief's “no commit on no change” is subject to its explicit keep-alive exception.

### D9 — Email and same-host schedule monitoring

`scripts/reaudit/notify.ts` uses existing nodemailer with implicit TLS `smtp.gmail.com:465`, IMAP_USER/IMAP_PASSWORD, fixed recipient, disabled protocol/debug logging and bounded timeouts. A safe structured Failure summary, not a raw Error/string dump, forms the body. Include old/candidate versions when available, stage, run URL, and cleanup/publication state. Failed email does not turn a failed audit green or recursively send another email. Provide `--selftest` to send a clearly labeled harmless failure-path proof without detection, commits or publication.

Add `.github/workflows/reaudit-watchdog.yml` and `scripts/reaudit/watchdog.ts` as auxiliary implementation of the locked schedule-stopped notice: independent daily trigger/manual dispatch, read-only Actions/contents permissions, Gmail secrets only. Query the real audit workflow's active/disabled state and recent run timestamps; consider a last-started run older than 48 hours overdue and alert on a disabled workflow. Separate failed-run notice from missed-trigger notice; do not treat a merely failed audit as proof the schedule stopped. No new host or credential is introduced. This independent workflow can detect reaudit.yml being disabled or missed while its own scheduler still works; it cannot detect total Actions silence until execution resumes.

### D10 — Retain evidence, not packages or raw responses

Reuse `redact`, `sanitizeZip`, `findSecret` from `test/plugin/artifacts.ts`; wrap child environments so scanning/unzip children do not receive unrelated secrets. Keep safe version/digest/gate/lifecycle facts, normalized reason codes and run URLs. Never retain GPL Vault response bodies, signed download URLs, HTTP queries, decrypted sources, WordPress database snapshots or paid ZIPs in Actions artifacts. Keep private scratch separate from the directory eligible for artifact upload.

Use synthetic stand-ins for unit privacy failures, including encoded secrets and malicious incoming URLs. In real checks assert booleans/counts rather than passing credential-bearing objects to matchers. On sanitation failure withhold/delete unsafe artifacts and fail before publication; still attempt a fixed safe failure email. Scan release ZIP entries as well as manifest/signature. A green scanner is known-secret evidence, not proof every possible private field was discovered.

### D11 — Current-version documentation is derived; historical limitations stay historical

Replace duplicate “current supported stack” claims with marked generated sections or links to the authoritative table. Have bump.ts regenerate the plugin's supported-version table/helper-version line and any deliberately retained current stack sections from the same pins. Test these generated sections for drift. Do not blindly replace every version in prose: callback source-line evidence and known-limitations paragraphs describe specific historical audits, not proof for all future versions. Label those historical and explain that newer pins pass the automated gate, not a new manual callback-body review. Keep synthetic updater versions documented as fixtures.

### D12 — Scope and unresolved limits

No helper update-client changes, checker policy changes, new paid source protocol, code-diff/LLM review, operator-per-release approval or client-site rollout. The one-time manual helper upgrade on sites stays outside this leaf.

Real limitations to preserve in plan/report/docs:
- Tests plus inventory assertions cannot detect all changed behavior inside an accepted callback, unexercised module or raw PHP networking path. This is the operator-accepted audit-depth risk.
- SIGKILL, runner loss or an unreachable GPL Vault deactivation service can strand an activation. Cleanup is required and verified when reachable, not guaranteed under process death.
- The locked request for an email if the schedule stops is only partially achievable with GitHub-hosted components alone. The separate watchdog covers one stopped audit workflow, not a platform-wide scheduler outage or both workflows disabled by inactivity. An unconditional independent outage guarantee needs a separately authorized external monitor; none is invented here. Flag this explicitly in review rather than call it proven.
- SMTP acceptance is not universally guaranteed delivery; first live notice evidence must separately confirm arrival. If Gmail itself is down, log a safe failure and keep the run failed.
- Keep-alive and daily triggering need elapsed-time evidence; fixtures prove decision boundaries, not GitHub's future scheduling guarantees.
- Source main update and release publication are not transactional. Inspect partial state before recovery.

## Needed interfaces

- `scripts/reaudit/bump.ts`: validated deterministic source/doc transformations from old pins and helper version to candidate pins/next patch; allowlisted changed paths.
- `scripts/reaudit/run.ts`: stage ownership, isolated environment construction, bounded child execution, candidate/summary output; no secret side effects on import.
- `scripts/reaudit/publish.ts`: candidate validation, main/tag checks, deterministic reconstruction, commit/push, existing release CLI, independent release verification.
- `scripts/reaudit/notify.ts`: safe summary → one bounded SMTP attempt, plus real selftest entry point.
- `scripts/reaudit/heartbeat.ts`, `watchdog.ts`: safe main-only heartbeat and read-only Actions liveness check respectively.
- `scripts/reaudit/setup.ts`: explicit one-time ciphertext/secret provisioning; not called by unit tests.
