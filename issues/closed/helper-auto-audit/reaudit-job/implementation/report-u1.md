# Unit 1 fixture repair: restoration was not reliable

Repair commit: `00c743c` (detached). It is a new commit whose parent is `b120086`, the landed pin refactor (lane `0d32481`), and it does not amend it. Worktree: `issues/worktrees/reaudit-job-u1`.
Briefs: `brief-1-fixture-repair.md` (repair worker: diagnosis, fix, red/green and focused native proof; the host reboot at 2026-10-06T10:34:54Z killed it before the broad run finished) and `brief-1-fixture-remainder.md` (this resume: broad verification with native gh, commit and report).
Evidence: `implementation/evidence-u1-fixture-repair/`.

Diagnosis (evidence, not hypothesis):
- B's lane failure, nested SMTP mutation in `Pro at the next patch`: received `1494637c…`, which is exactly the altered FluentSMTP boot.php (2.4.1 → 2.4.2), where `a6966aa3…` (original) was expected. `red-digests.txt` and `green-compatibility-mutation-notes.jsonl` record both digests.
- `probe-old-mechanism.log` comes from a temporary probe (`probe-old-mechanism.test.ts.txt`; the probe file was removed from the tree). It ran the exact old PHP steps (copy to a fixed `.pirax-original`, file_put_contents, then rename back in a separate request) for 8 cycles and recorded each return value and readback. Cycles 0–2 restored correctly. In cycle 3, worker pid 5 ran the edit again after another worker had renamed the backup away. `copy()` returned false with `Failed to open stream: No such file or directory`, while `file_exists()` on the backup still returned true and reading it gave false. The unchecked `file_put_contents` then installed the edit, and the later `rename()` failed with ENOENT. The file stayed altered from then on.
- Cause: Playground's workers share the site directory, but each worker caches the file names it has seen. A fixed backup name reused across requests on different workers therefore fails on a later edit, and the old helper never checked copy/write/rename. Opcache and cross-request visibility of the new content were not the cause: fresh reads on all workers saw the current bytes once the writes really happened.

Changed files and reasons:
- `test/plugin/version-fixtures.ts`: new shared `withAlteredFile(h, file, search, replace, body)`. Each edit gets a new `…pirax-original-<UUID>` backup. The backup copy, the edit and the restore rename are each checked. The backup and the edit are read back by SHA-256 so a failure throws instead of leaving the edit installed. The restored-byte assertion `expect(restored).toBe(hashes.original)` is kept. `body` receives the original and altered hashes.
- `test/plugin/compatibility.test.ts`: the local `withAlteredFile` (unchecked copy/write/rename on a fixed name) is replaced with a thin wrapper around the shared helper. It still writes the `altered vendor fixture` evidence note. Every version-only/generic refusal assertion is unchanged.
- `test/plugin/harness.test.ts`: new regression `withAlteredFile: repeated and nested plugin edits reach every Playground worker and restore the original bytes`. It runs 7 edit → fresh read → restore cycles on fluentform.php (so the restore runs on another worker and an earlier backup's worker edits again), then 2 nested rounds (FF define outer, GF header inner). Every round checks with 7 fresh reads, one per worker in the round-robin plus one, that each worker sees exactly the current edits and, afterwards, the originals.
- No production code, pins, callbacks or helper version changed.
